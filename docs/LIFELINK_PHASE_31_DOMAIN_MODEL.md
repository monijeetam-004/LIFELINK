# LifeLink Phase 31 — Domain Model Inventory

Built per the Phase 31 master prompt's Section 2 requirement: a verified inventory of the actual current implementation, produced *before* any code change, by direct source inspection (this document) plus seven parallel read-only investigation agents whose findings were independently spot-checked against source. No entity below is invented — every row cites the real model/file it comes from. Where an entity named in the master prompt's checklist has no distinct model (e.g. "BLOOD UNIT"), that is stated explicitly rather than silently glossed over.

Conventions: `app/models/X.py` paths are relative to `backend/`. "Lifecycle" lists the actual enum values in the codebase, in the order declared — not an idealized state machine.

## 1. USER / ROLE

**Model**: `User` (`app/models/user.py`). **Role enum**: `UserRole` = `PATIENT | FAMILY | DONOR | HOSPITAL | ADMIN`.

| Field | Purpose |
|---|---|
| `email` (unique, indexed) | Login identity |
| `password_hash` | bcrypt hash (`app/core/security.py`) |
| `full_name` | Display name |
| `role` | Fixed at registration; changed only via `POST /admin/users/{id}/role` |
| `is_email_verified` | Gates login until OTP-verified |
| `is_active` | False = suspended; `get_current_user` rejects immediately |
| `password_changed_at` | Session invalidation anchor (`app/core/session_service.py`) |
| `suspended_reason` / `suspended_at` / `suspended_by_user_id` | Admin suspension audit trail |

Created by: self-registration (`POST /auth/register`) or nothing else — there is no admin "create user" endpoint. Modified by: the user themselves (name/password), or an admin (role/suspend/reactivate). Viewed by: self (`/auth/me`), admin (`/admin/users`). Validation: email format + uniqueness, password strength (`app/core/security.py`). DB constraints: unique index on `email`. Concurrency: role/suspend changes are single-row `UPDATE`s with no lock — acceptable because they're rare, admin-only, and idempotent-by-nature (setting `is_active=False` twice has no different effect than once). Frontend: every portal's auth context; `AdminUsers.tsx`. Tests: `test_auth_flow.py`, `test_auth_hardening_phase7.py`, `test_admin.py`.

Role-specific profile data lives in **separate** 1:1 tables, not on `User` itself — see PATIENT/DONOR/HOSPITAL below.

## 2. PATIENT

**Model**: `PatientProfile` (`app/models/profile.py`), 1:1 with a `User` of role PATIENT (created lazily via `get_or_create_patient_profile`, `app/services/domain_service.py` — there is no explicit "become a patient" step). Fields: `blood_type`, `date_of_birth`, `phone`, `address`, `city`, `medical_notes`, `emergency_contact_name`, `emergency_contact_phone`. No lifecycle/status — a profile simply exists or has defaults. Created/modified by: the patient themselves (`PUT /patients/me`) or a FAMILY member with an ACCEPTED `FamilyLink` acting on their behalf (`resolve_beneficiary`, `app/services/domain_service.py`). Viewed by: self, linked family, the hospital handling one of their requests, admin. Validation: blood type must be a real `BloodType` enum value; no server-side validation of `medical_notes` content (free text, correctly — this is not medical software providing clinical guidance). Frontend: `PatientProfile.tsx`, `PatientDashboard.tsx`.

## 3. FAMILY

Not a separate profile table — a FAMILY-role `User` has no profile of its own beyond `User` itself. The entity that matters is the **link** between a family member and a patient:

**Model**: `FamilyLink` (`app/models/family.py`). Lifecycle (`FamilyLinkStatus`): `PENDING → ACCEPTED | REJECTED`, plus `REVOKED` and `EXPIRED` (an accepted or pending link can lapse). Fields: `family_user_id`, `patient_user_id`, `relationship` (free text, e.g. "spouse"), `status`, `requested_by_user_id` (either side can initiate), `expires_at` (a PENDING invite that's never accepted), `reason` (rejection/revocation reason), `responded_at`. Created by: either the family member or the patient (`POST /family/link-requests`). Modified by: the patient accepts/rejects; either side can later revoke an ACCEPTED link. Viewed by: both parties, admin. Validation: cannot link to yourself; cannot create a second PENDING/ACCEPTED link for the same pair (checked, see Section 18 of the audit for the concurrency finding). DB constraints: FKs on both user columns with `ondelete="CASCADE"`. Lazy expiry: `_expire_if_stale` in `app/api/routes/family.py` — same no-scheduler-exists pattern as blood requests/emergencies. Frontend: `FamilyDashboard.tsx`, `ManageLinkedPatients.tsx`. Tests: `test_family.py`, `test_phase13_family_link_security.py`.

## 4. DONOR

**Model**: `DonorProfile` (`app/models/profile.py`), 1:1 with a DONOR `User`. Key fields: `blood_type`, `last_donation_date` (drives eligibility, see below), `is_available` (bool) and `availability_state` (`DonorAvailabilityState`: `AVAILABLE | UNAVAILABLE | NOT_NOW` — two overlapping availability signals, documented as a known redundancy in prior-phase reports, not re-litigated this phase since neither is incorrect), `weight_kg`, `medical_conditions` (free text, never interpreted by any rule engine — see Section 6 below), `latitude`/`longitude` + `share_location` (opt-in geolocation), `identity_verified` (only ever set by `verification_service` on admin approval — never self-settable), `alert_min_urgency` / `alert_radius_km` (notification preferences, not eligibility). Created by: `get_or_create_donor_profile` on first `PUT /donors/me`. Eligibility is **computed, not stored**: `app/core/eligibility.py::is_eligible(last_donation_date)` applies a fixed 56-day interval (documented as the only rule this codebase claims, with no citation to a named blood-bank authority — flagged in the audit as a fact requiring a real regulatory source before being treated as medically authoritative). Frontend: `DonorProfile.tsx`, `EligibilityCheck.tsx`, `ReadyConsole.tsx`, `AlertWatcher.tsx`. Tests: `test_donor_matching.py`, `test_alert_watcher.py`.

## 5. HOSPITAL / BLOOD BANK

**Model**: `HospitalProfile` (`app/models/hospital.py`), 1:1 with a HOSPITAL `User`. Fields: `name`, `license_no`, `phone`, `address`, `city`, `latitude`/`longitude`, `verified` (bool — set only by `verification_service` on admin approval of a `HOSPITAL_FACILITY` verification request), `facility_type` (`FacilityType`: `HOSPITAL | BLOOD_BANK` — the single model covers the master prompt's "HOSPITAL" and "BLOOD BANK" as one facility-type-discriminated table, not two separate entities; this is a deliberate, documented modeling choice, not a missing entity). No independent lifecycle beyond `verified`. Created by: `get_or_create_hospital_profile` on first `PUT /hospitals/me`. Frontend: `HospitalDashboard.tsx`, directory listing in `HospitalDirectory.tsx`/patient-facing donor search. Tests: `test_hospital.py`.

## 6. ADMIN

No separate profile — `User.role == ADMIN` is the entire model. Admin capabilities are enforced per-route via `require_roles(UserRole.ADMIN)` (`app/api/deps.py`), never a client-side check. Frontend: the entire `Admin*.tsx` set under the admin portal. Tests: every `test_admin*.py` file plus per-feature admin-only assertions embedded across the suite.

## 7. BLOOD REQUEST

**Model**: `BloodRequest` (`app/models/blood_request.py`). Lifecycle (`BloodRequestStatus`): `PENDING → MATCHING → FULFILLED`, with `CANCELLED`/`EXPIRED` reachable from any open state. Transition table: `app/core/request_lifecycle.py` (pure, DB-free); DB-touching half `app/services/blood_request_lifecycle.py` (row-locking via `get_for_update`, lazy `expire_if_stale`). Fields: `requester_user_id`, `patient_user_id` (may differ — a FAMILY member can file for a patient), `blood_type`, `units_needed`, `urgency` (`Urgency`: `ROUTINE|URGENT|CRITICAL`), `status`, `hospital_name`/`city`/`note` (free text context, not FK'd to a real `HospitalProfile` — a real, documented limitation: a request names a hospital by string, it does not require the named hospital to exist or confirm anything by that name alone), `needed_by` (drives lazy expiry), `fulfilled_at`/`cancelled_at`/`expired_at`, `latitude`/`longitude`, `idempotency_key` + `idempotency_payload_hash` (Phase 19 addition — safe retry of `POST /blood-requests`). Created by: patient or family-on-behalf. Modified by: requester/family (cancel), a donor (`DonorResponse`, see below), a hospital (`HospitalRequestResponse`), admin (direct status override with audit trail). Viewed by: requester, linked family, matching donors (anonymized list), any hospital, admin. **Quantity invariant actually enforced**: `units_needed` is a fixed target set at creation; `FULFILLED` is only reached by the requester/hospital explicitly calling `POST /blood-requests/{id}/fulfill` with the donations being credited — a single accepted donor does **not** auto-fulfill a multi-unit request (verified by direct code read of `fulfill_request`, `app/api/routes/blood_requests.py`). There is, however, no dedicated `PARTIALLY_FULFILLED` status — a request with some but not all units covered stays `MATCHING`, and "how many units are actually covered so far" is derivable only from the linked `Donation` rows, not a first-class stored field. This is documented in the audit as a valid, minor gap (Section 10), not fixed this phase (adding a redundant status without also redesigning donation-crediting bookkeeping would risk introducing a mismatch between two sources of truth). Tests: `test_blood_requests.py`, `test_blood_request_lifecycle_phase10.py`, `test_phase19_blood_request_idempotency.py`.

**Sub-entities**:
- `BloodRequestEvent` — append-only user-facing timeline (`event_type`, `note`, `actor_user_id`, `created_at`). Never updated or deleted.
- `DonorResponse` — a donor's accept/decline against one request. `DonorResponseStatus`: `ACCEPTED | DECLINED | NOT_NOW`. Unique on `(request_id, donor_user_id)`.
- `HospitalRequestResponse` — a hospital's operational response. `HospitalResponseStatus`: `ACKNOWLEDGED → PREPARING → DISPATCHED → ... → ALLOCATED → FULFILLED`, or `DECLINED`. Distinct from `DonorResponse` — a hospital is coordinating logistics, not personally donating (see Section 12 of the audit, and `donor_commitment.py`'s docstring for why this distinction matters for the Phase 31 double-booking fix).

## 8. EMERGENCY / SOS

**Model**: `Emergency` (`app/models/emergency.py`). Lifecycle (`EmergencyStatus`): `ACTIVE → ACKNOWLEDGED → MATCHING → ASSISTANCE_FOUND`, terminal `RESOLVED`/`CANCELLED` reachable from any open state; `MATCHING → ACKNOWLEDGED` is also legal (every accepted responder withdrew — the emergency "reopens"). Transition table: `app/core/emergency_lifecycle.py`; DB half `app/services/emergency_lifecycle.py`. Fields: `created_by_user_id`, `patient_user_id`, `blood_type`, `urgency`, `status`, `location_text`, `note`, `resolved_at`, `units_needed`, `deadline`, `idempotency_key`, `target_facility_id` (optional named facility), and — **new this phase** — `deadline_exceeded_at` (nullable; set exactly once by `flag_deadline_exceeded_if_needed` the first time any read/mutating route notices `deadline` has passed on a still-open emergency; never changes `status` — see the audit's Section 9 finding and fix). Created by: patient or family-on-behalf (never a donor/hospital — `POST /emergencies` is patient/family-only, verified by `require_roles`). Modified by: creator/patient/linked-family (acknowledge is donor/hospital/admin; accept/decline is any responder; assistance-found/cancel/resolve is the manager set). Viewed by: creator, linked family, candidate responders (open list), admin. Tests: `test_emergencies_and_notifications.py`, `test_phase12_emergency_sos_engine.py`, `test_phase31_domain_fixes.py`.

**Sub-entities**:
- `EmergencyResponse` — a donor's or hospital's accept/decline. Same `DonorResponseStatus` enum reused (not a separate emergency-only status set — a deliberate reuse, not a gap). Unique on `(emergency_id, responder_user_id)`.
- `EmergencyEvent` — append-only timeline, same pattern as `BloodRequestEvent`.
- `EmergencyPathway` (`app/models/emergency_pathway.py`) — a versioned resource-routing decision for one emergency. Fields: `version`, `status` (`EmergencyPathwayStatus`: `ACTIVE|SUPERSEDED`), `origin_facility_id`, `selected_facility_id`, `pathway_source` (`GraphPathwaySource`: `GRAPH|HAVERSINE_FALLBACK` — honest provenance, never claims graph-verified when it fell back), `distance_km`, `transit_minutes`, `hops`, `graph_available`, `reason`, `superseded_at`/`superseded_reason`. Partial unique index `uq_emergency_pathway_one_active` enforces "at most one ACTIVE version per emergency" at the DB level. Re-optimized automatically when `admin.disrupt_transport_route` disrupts a route the current pathway depends on (`emergency_pathway_service.handle_route_disrupted`).

## 9. DONATION

**Model**: `Donation` (`app/models/donation.py`). No status/lifecycle enum at all — a donation is a **fact record**, not a workflow object: it is logged after the fact (`POST /donors/me/donations`) with `units`, `donated_on`, `hospital_name`, optional `blood_request_id` (crediting a specific request), `idempotency_key`/`idempotency_payload_hash` (Phase 26 addition). This is a deliberate, correct modeling choice — a completed donation has nothing left to transition through. Created by: the donor themselves, self-reported (there is no hospital-side "confirm this donation actually happened" step — see the audit's Section 12 finding: donation logging is honor-system / self-attested, and this is disclosed, not hidden, since the frontend never claims hospital confirmation it doesn't have). Read by: the donor, admin, and `Certificate` issuance (1:1, see below).

## 10. BLOOD UNIT / BLOOD INVENTORY / BLOOD COMPONENT

**No `BloodUnit` model exists.** Inventory is tracked as **aggregate counts per (hospital, blood type)**, not individually-tracked physical units:

**Model**: `HospitalInventory` (`app/models/hospital.py`). Fields: `hospital_id`, `blood_type`, `units` (available count), `reserved_units` (earmarked but not yet allocated). No per-unit collection date, expiry, or donor traceability — a unit is a number, not a row. This is the single most consequential finding of the Phase 31 domain audit (see the audit document's Section 3): the master prompt's suggested `COLLECTED → TESTING → CLEARED → AVAILABLE → RESERVED → ALLOCATED → DISPATCHED → RECEIVED → TRANSFUSED` per-unit lifecycle **does not exist**, and was evaluated and **deliberately not implemented this phase** — see the audit's justification (real transactional integrity already exists at the aggregate level via `HospitalInventoryLog`, and inventing per-unit tracking without a real barcode/collection pipeline behind it would be decorative complexity, not a real fix, violating Section 34's "do not add features merely because they sound impressive").

Every mutation is logged: `HospitalInventoryLog` (append-only) records `action` (`HospitalInventoryAction`: `ADD|RESERVE|ALLOCATE|RELEASE|EXPIRE|RECONCILE`), `delta_units`/`delta_reserved`, `resulting_units`/`resulting_reserved` (post-mutation snapshot — makes every log row independently auditable without replaying history), `actor_user_id`, optional `request_id`/`emergency_id` (which demand this mutation served), `note`. All inventory mutations go through `app/services/inventory_service.py`, which locks the `HospitalInventory` row (`with_for_update`) before mutating and enforces non-negative `units`/`reserved_units` via a CHECK constraint at the DB level (belt-and-suspenders: application-level validation plus a constraint that survives an application bug).

**No `BloodComponent` model exists** — every request/inventory/donation is Whole-Blood-equivalent by `BloodType` alone; RBC/Plasma/Platelets are not distinguished anywhere in the schema, API, or frontend. This is Section 4's audit finding, evaluated and **not implemented this phase** (see the audit for the medical-safety reasoning: component-specific compatibility rules are a real clinical fact this codebase has no authoritative source for, and inventing one would violate Section 35's explicit prohibition).

## 11. MATCH / DECISION TRANSPARENCY

Not a persisted entity — a match is a **computed ranking**, produced fresh on each request by `app/core/matching_engine.py` (`rank_candidates`) and returned as `MatchFactorsOut` (structured factors: compatibility, availability, distance, urgency-fit, has-accepted) plus a human-readable `explanation` string. Nothing about a match is stored once computed; re-running the same query against unchanged data reproduces the same ranking deterministically (verified by the tuple-based sort key design — no randomness, no external state). See the audit's Sections 7-8 for the staged-pipeline verification and the deliberate absence of a weighted "trust score."

## 12. NOTIFICATION

**Model**: `Notification` (`app/models/notification.py`). Fields: `user_id`, `type` (free-form string tag, e.g. `"blood_request.new"`, `"emergency.deadline_exceeded"`), `title`, `body`, `data` (JSON payload for frontend deep-linking), `read_at`, `created_at`. No delivery-status lifecycle on this row itself — it represents "this in-app notification exists," full stop; email/SMS are separate, optional side-channels (`_maybe_send_email`/`_maybe_send_sms` in `app/services/notification_service.py`) whose own success/failure never affects this row. `NotificationPreference` (`app/models/notification_preference.py`) holds per-user opt-in/quiet-hours/digest-frequency settings. `SmsNotification` (`app/models/sms_notification.py`) is SMS's own audit trail with a real `SmsStatus`/`SmsFailureCategory` lifecycle (SMS is off by default in every deployment — see `LIFELINK_SMS_STATUS.md`). See the audit's Section 16 for the full delivery-semantics classification (best-effort, at-most-once for email, never claimed as "delivered" merely because SMTP accepted the send).

## 13. VERIFICATION

**Model**: `VerificationRequest` (`app/models/verification.py`). Lifecycle (`VerificationStatus`): `PENDING → APPROVED | REJECTED`. Kinds (`VerificationKind`): `DONOR_IDENTITY | HOSPITAL_FACILITY`. Fields: `user_id`, `kind`, `status`, `documents` (list of `{key, filename, content_type, size}` — object-storage references, never raw bytes in the DB), `note`, `reviewer_user_id`, `review_note`. **New this phase**: partial unique index `uq_verification_one_pending_per_kind` on `(user_id, kind) WHERE status = 'PENDING'` — closes a real check-then-insert race (see the audit's Section 19/23 finding and fix). Approval is the *only* code path that sets `DonorProfile.identity_verified` / `HospitalProfile.verified` (verified by direct read of `verification_service.py` — no other route touches those fields). No document versioning across resubmission (a rejected-then-resubmitted request is a brand-new row, which is arguably correct — a resubmission is a new claim, not an edit of the old one — but means there's no single-row history of "this person tried 3 times"; documented as a valid limitation, not fixed). Tests: `test_verifications.py`, `test_phase14_verification_security.py`, `test_phase31_domain_fixes.py`.

## 14. CERTIFICATE

**Model**: `Certificate` (`app/models/certificate.py`). 1:1 with a `Donation` (unique FK). Fields: `donation_id`, `donor_user_id` (denormalized owner), `serial` (unique), `verify_code` (unique, non-guessable, public), `storage_key` (the rendered PDF). **New this phase**: `revoked_at`/`revoked_by_user_id`/`revocation_reason` (nullable — see the audit's Section 20 finding and fix: before this phase a certificate could never be invalidated once issued). Created by: the donor themselves, self-issued from their own logged `Donation` (`POST /certificates`) — there is **no hospital confirmation step** behind certificate issuance; it attests "a donation was logged," not "a hospital confirmed this donation occurred." This is disclosed as a real, documented trust-model limitation in the audit (Section 20), not silently implied to be hospital-verified. Public verification (`GET /certificates/verify/{code}`) now honestly reflects revocation (`valid: false` once revoked) rather than only ever reporting "exists = valid." Tests: `test_certificates.py`, `test_phase15_certificate_security.py`, `test_phase31_domain_fixes.py`.

## 15. TRANSPORT / TRANSPORT ROUTE / PATHWAY

**Model**: `TransportRoute` (`app/models/transport.py`). Lifecycle (`TransportRouteStatus`): `OPERATIONAL | DISRUPTED` — a binary, not the richer multi-state lifecycle the master prompt suggests (`AVAILABLE/ASSIGNED/EN_ROUTE_TO_SOURCE/...`). Evaluated in the audit (Section 14) and **not expanded this phase**: the richer lifecycle models a specific physical vehicle's journey, but this codebase has no vehicle/shipment entity at all — routes are edges in the facility graph (Neo4j-backed, with Haversine fallback), not dispatched trips. Expanding the status enum without a real dispatch/tracking system behind it would be decorative. What *is* real and verified: disrupting a route (`admin.disrupt_transport_route`) synchronously triggers `emergency_pathway_service.handle_route_disrupted`, which finds every open emergency whose *current* pathway actually depended on that route and re-optimizes it for real — pathway feasibility does reflect transport reality, not a stale cache (the master prompt's core requirement for this entity, confirmed correct). `GraphPathwayLog` (`app/models/graph_pathway_log.py`) is the append-only audit trail of every resource-pathway query, recording `pathway_source`, `graph_available`, `disrupted_routes_excluded` for provenance.

## 16. AUDIT EVENT

**Model**: `AuditLog` (`app/models/audit_log.py`). Fields: `actor_user_id` (nullable — a `None` actor is used for genuinely system-initiated events like the deadline-exceeded flag, never to hide a real actor), `action` (namespaced string, e.g. `"emergency.deadline_exceeded"`, `"admin.certificate_revoked"`), `target_type`/`target_id`, `ip`, `user_agent`, `meta` (JSONB — structured old/new state, reasons), `created_at` (server-default `now()` — server clock, not client-suppliable, so it can't be backdated by a malicious request). Append-only: no route ever updates or deletes an `AuditLog` row (verified by grep — `audit_service.record` is insert-only). Read by: admin only (`GET /admin/audit-log`), with filters on action/actor/role/target/severity/date range and offset-based pagination. See the audit's Section 21 for the hash-chain tamper-evidence evaluation (not implemented — see reasoning there).
