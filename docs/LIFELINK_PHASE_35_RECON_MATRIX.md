# LifeLink — Phase 35 Reconnaissance: Implementation Matrix

This is the Phase A deliverable for the "Final Production-Grade System Completion & Real-Time Hardening Phase" master prompt. Every row below was verified against the actual current code (not inferred from prior phase reports) on 2026-10-05. Where a prior report's "remaining work" item turned out to already be closed, or partially closed, that is called out explicitly — the master prompt requires this before any new code is written.

**Scale note, stated up front rather than discovered later**: this master prompt's 43 sections describe roughly the same amount of work as Phases 31 through 34 combined, times three — each of those phases was a single, fully-scoped, fully-verified unit of work in this project's own history. Treating all 43 sections as one atomic deliverable would force a choice between (a) claiming completion without the real migration/concurrency/E2E verification this project has required at every phase so far, or (b) being honest that depth was traded for breadth. Per the master prompt's own Section 43 ("honest limitations > fake completeness"), this phase proceeds as the master prompt's own Section 39 ordering (Phase A→L), each sub-phase implemented with the same rigor as every phase before it — real migrations, real Postgres concurrency tests, real regression — and reported on as it completes, rather than attempted all at once. This document is Phase A. Implementation begins immediately after it with Phase B/C.

## Phase B/C completion report (blood component model, unit identity, donation traceability, defense-in-depth compatibility)

**What was built**, closing matrix rows "Blood component model," "Donation → unit traceability," "Unit identity," and "Inventory allocation defense-in-depth" above:

- `BloodComponent` enum (`WHOLE_BLOOD`/`RED_BLOOD_CELLS`/`PLASMA`/`PLATELETS`) on `BloodUnit`, `HospitalInventory`, and `HospitalInventoryLog`, defaulting to `WHOLE_BLOOD` and backfilled to it on every pre-existing row (migration `b1c2d3e4f5a6`) — the only component this system ever tracked before this phase, so every existing row's meaning is unchanged.
- `app/core/clinical_sources.py` — shelf-life figures for all four components, each with a named source organization, source document, URL, and fetch date (AABB Circular of Information; American Red Cross Compendium of Transfusion Practice v.04 Jan 2021; Australian Red Cross Lifeblood), including an explicitly disclosed limitation (FFP's real-world 24-hour post-thaw window is not enforced by this system, only its frozen shelf life).
- `app/core/component_compatibility.py` — dispatches `WHOLE_BLOOD`/`RED_BLOOD_CELLS` to the unchanged existing red-cell engine; implements a separately-sourced, ABO-only, donor/recipient-inverted table for `PLASMA` (source: UTMB Blood Bank ABO Compatibility Chart); treats `PLATELETS` as never ABO-restricted.
- `BloodUnit.unit_code` — globally unique, human-readable (`LL-<BLOODTYPE>-<COMPONENT>-<8hexuppercase>`), contains no donor PII, backfilled for every pre-existing unit.
- `BloodUnit.donation_id` — optional traceability link to `Donation`, settable only via `add_stock`'s new `donation_id` parameter, integrity-checked by `_assert_donation_can_justify` (invariant 21 in `LIFELINK_INVARIANTS.md`).
- `inventory_service._assert_context_compatible` — defense-in-depth re-verification of component-aware compatibility inside `reserve_stock`/`allocate_stock` whenever a `request_id`/`emergency_id` is given (invariant 22).
- Every `inventory_service` action function threaded `component` through; `app/api/routes/hospitals.py` wired `InventoryActionIn.component`/`.donation_id`/`InventoryReconcileIn.component` from the request body to every call site (`_do_inventory_action`, `add_inventory`, `expire_inventory`, `reconcile_inventory_one`, `allocate_to_request`).

**Bugs found and fixed during this sub-phase (not just assumed correct):**

1. **`_inventory_map` cross-component collision** (`app/api/routes/hospitals.py`): the legacy GET/PUT `/hospitals/me/inventory` helper queried every `HospitalInventory` row for a hospital and keyed a dict by `blood_type` alone. Once a second component could exist for the same blood_type, this would silently collapse two real rows onto one dict entry, non-deterministically. Fixed by filtering `component == WHOLE_BLOOD` explicitly, preserving the byte-identical legacy contract. Caught by code inspection before it shipped, not by a failing test.
2. **Admin facility-detail honesty gap** (`app/api/routes/admin.py` / `app/schemas/admin.py`): `get_facility`'s inventory listing would render two real rows for the same blood_type (e.g. `WHOLE_BLOOD` and `PLATELETS`) as two identically-labeled lines with no way for an admin to distinguish them. Fixed additively by adding `component` to `AdminFacilityInventoryLineOut` and sorting the query by `(blood_type, component)`. Verified: `tests/test_phase35_blood_component.py::test_admin_facility_detail_distinguishes_components_for_the_same_blood_type`; existing `test_admin.py`/`test_admin_phase6.py` re-run green (purely additive field).
3. **Real concurrency bug in donation-traceability integrity** (`inventory_service._assert_donation_can_justify`): the original implementation counted already-linked units with no lock. Two concurrent `add_stock` calls citing the *same* `donation_id` but *different* `blood_type` values (so they never contend on the same `HospitalInventory` row — the only other lock in this module) each independently read `already_linked=0` and both passed the check. **Confirmed by direct real-Postgres/real-thread experiment**: a 2-unit donation ended up with 4 linked `BloodUnit` rows. Fixed by locking the `Donation` row itself (`SELECT ... FOR UPDATE`) inside the check, so the second concurrent caller blocks until the first's transaction ends and then re-reads a genuinely current count. Regression test (`test_concurrent_add_against_same_donation_never_over_claims`) deliberately uses two different blood types so it cannot pass by accident via the unrelated `HospitalInventory` unique constraint — the same mistake that let the original bug through unnoticed if tested carelessly.

**Tests**: new file `tests/test_phase35_blood_component.py`, 14 tests — backward compatibility, component isolation, unit_code uniqueness/format, donation traceability integrity (including the real-concurrency race above), defense-in-depth compatibility rejection (plasma's inverted table catching what the red-cell engine alone would have missed), and the admin-honesty regression. Full existing backend suite (60 files, all pre-Phase-35 tests) re-run clean in isolated sequential chunks after every change in this sub-phase — zero regressions.

**Deliberately not done in this sub-phase** (tracked separately, per the master prompt's own Section 39 ordering): a new component-level inventory visibility endpoint (e.g. `GET /hospitals/me/inventory/components`) was considered and deferred — nothing in the frontend consumes component-aware data yet, so shipping an endpoint with no caller would be speculative rather than needed; it will be added in Phase G (frontend integration) only if the frontend work actually calls for it, per Section 38's "no speculative generality" constraint. `app/api/routes/emergencies.py`'s inventory calls were reviewed and deliberately left at the `component` default (`WHOLE_BLOOD`) — emergencies have no component-specific UI today, so there is nothing for a caller to honestly pass.
