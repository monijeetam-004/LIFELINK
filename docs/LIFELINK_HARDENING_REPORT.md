# LifeLink — Final H→L Completion + Production Hardening Report

**Date:** 2026-10-06 · **Machine for every number below:** sandbox VM, 2 vCPU (Intel Xeon @ 2.80 GHz), 8 GB RAM, PostgreSQL 16.13, Redis 7.0.15, Python 3.11.15 (dev venv; the hashed lock targets 3.12 and was verified with a 3.12 venv), Node/Vite build, Chromium (Playwright). Load generator and server share the machine.

This report covers the hardening round requested after Phase L. Phases H–L were re-verified (full suites below) rather than redone; no regression was found that required redoing a phase. Every claim is labelled by what was actually executed. Companion docs: `LIFELINK_EMAIL_VERIFICATION.md`, `LIFELINK_MALWARE_SCANNING.md`, `LIFELINK_AUDIT_CHAIN.md`, `LIFELINK_REALTIME_EVENTS.md`, `LIFELINK_DEPENDENCIES.md`, `LIFELINK_THREAT_MODEL.md` (addendum), `LIFELINK_INVARIANTS.md` (48–52), `LIFELINK_MASTER_COMPLETION_STATE.md` (A–E classification). Raw measurement output: `docs/perf_evidence/hardening/`, `docs/evidence/`.

## 1. Security

### 1.1 Email verification — implemented and enforced end to end
Found: tokens and endpoints existed, **enforcement did not** (an unverified account could use the whole API). Now `get_current_user` returns 403 (`X-LifeLink-Reason: email-unverified`) on every route except me/logout/change-password; the frontend redirects to `/verify-email`. Tokens single-use, expiring, stored hashed; resend supersedes; no enumeration. 7 backend tests + 1 Vitest, all executed and passing. Not verified: delivery via a real SMTP provider.

### 1.2 Malware scanning — implemented; real ClamAV exercised with a test-only signature DB
States `PENDING_SCAN / CLEAN / INFECTED / SCAN_FAILED`; quarantine prefix; only `CLEAN` is downloadable/approvable; scanner failure → quarantine + scheduled rescan, never clean; infected → 422, nothing stored, audited; admin rescan endpoint; production refuses `DOCUMENT_SCANNER=none`; migration `a6b7c8d9e0f1` withholds legacy unscanned documents. Real `clamd` (ClamAV 1.5.4) ran here **with an EICAR-only signature DB** (signature mirrors blocked), so the integration is proven, not ClamAV's detection breadth. Failure modes (timeout, garbage, closed connection, unreachable) exercised with a fake clamd. 16 backend + 2 Vitest tests. Docker/CI ClamAV containers: authored, not executable here.

### 1.3 Self-hosted assets + tighter CSP — implemented
25 `lh3.googleusercontent.com` mockup images → local SVGs (logo mark redrawn from the project's own logo, certificate seal, avatar, abstract illustration); Google Fonts → bundled npm fonts. CSP: `font-src 'self'`, `style-src 'self' 'unsafe-inline'`, `img-src 'self' data: https://*.tile.openstreetmap.org`. Built `dist/index.html` references no external host except the tile servers. Offline: everything renders except map tiles. Guarded by `selfHostedAssets.test.ts` (3 tests). The certificate PDF generated by the backend contains no images (unchanged).

### 1.4 Dependencies — hashed Python lock in CI and Docker; npm advisories audited
`requirements.lock` / `requirements-dev.lock` (uv, py3.12/x86_64, `--require-hashes --no-deps`) used by the Dockerfile and every CI Python job, with a lock-consistency CI step and `pip-audit` on the lock; update procedure in `LIFELINK_DEPENDENCIES.md`. npm: `source-map-js` advisory fixed (1.2.2). `braces` (high) and `postcss-selector-parser` (moderate) remain — **dev/build-time only, no patched release in Tailwind 3's range**; clearing them needs the Tailwind 4 migration, evaluated and deferred (visual regressions unverifiable here).

## 2. Audit hash chain — hardened (tamper evidence, still not immutability)

Threat model table in `LIFELINK_AUDIT_CHAIN.md`. Implemented and tested:
1. **Append-only guard** (PostgreSQL triggers, migration `c9d0e1f2a3b4`): refuses UPDATE of sealed entries, content edits of unsealed entries, DELETE and TRUNCATE (incl. `TRUNCATE users CASCADE`); the sealer still works. **The table owner can disable it** — the API must run as a non-owner role (deployment step; not executed here, the sandbox uses one role). Side effect found and handled: hard-deleting a user referenced by sealed entries is now refused (previously it silently rewrote sealed rows via `ON DELETE SET NULL` and broke the chain); `e2e_seed.py` now resets fixture users in place.
2. **HMAC-signed checkpoints outside the database**: key never in the DB, `prev_mac`-chained JSONL with `O_APPEND`+`fsync`, key rotation via retired keys, refuses to extend a broken log; endpoint `POST /admin/audit-log/checkpoint` and `scripts/audit_checkpoint.py write|verify [--incremental]`; verify endpoint reports checkpoint status; admin panel shows it. Detects: full recompute, truncation below a checkpoint, forged/edited/removed/reordered checkpoints, unknown key.
3. **Incremental verification** from the latest verified checkpoint (with its stated limitation proven by a test).
Not detectable (stated): owner role **plus** checkpoint key; removal of the newest checkpoint lines without append-only storage.

## 3. Real-time — hardened
- Publication moved off the request thread to a per-process background publisher (wake on commit + periodic drain every 5 s; inline mode retained). Tests: publication happens on the publisher thread; a backlog with no further writes is drained.
- SSE: one Redis pub/sub connection per process shared by all streams (`_Broker`), bounded per-stream queues, `resync` on lag or Redis loss. Measured: **200 open streams on 2 worker processes → 2 Redis pub/sub connections** (Phase F design: one per stream, i.e. 200).
- New events: `family_link.updated` (audience: the two parties) and `certificate.updated` (donor + ADMIN), client invalidation wired. 7 backend + 1 Vitest tests.

## 5. Load test (`scripts/loadtest_hardening.py`, production runner `run_production.sh`, `WEB_CONCURRENCY=2`, volume DB)

Closed loop, 20 s per level, weighted read-heavy mix of 12 real endpoints across donor/patient/hospital/admin (incl. one write), 121 seeded accounts. **This is a stress test on a shared 2-vCPU sandbox (server, Postgres, Redis and the generator on the same 2 cores) — not a production capacity figure.**

Warm, no SSE (`loadtest_nosse.txt`):

| C | req/s | p50 ms | p95 ms | p99 ms | errors | server CPU (% of 1 core) | server RSS |
|---|---|---|---|---|---|---|---|
| 1 | 34.7 | 18.5 | 95.0 | 175.9 | 0 | 72 | 359 MB |
| 8 | 60.9 | 86.8 | 389.1 | 518.7 | 0 | 135 | 382 MB |
| 32 | 52.9 | 490.1 | 1,341.5 | 2,321.5 | 0 | 128 | 444 MB |
| 64 | 47.1 | 1,156.5 | 2,787.9 | 3,677.3 | 0 | 128 | 466 MB |

Warm, with 200 open SSE streams held by the generator (`loadtest_sse.txt`): 26.8 / 24.7 / 40.6 / 42.1 req/s at C = 1/8/32/64, 0 errors, 2 Redis pub/sub connections throughout, idle cost of 200 streams ≈ 23 % of one core (`sse_idle.out`). The generator itself runs the 200 stream readers on the same cores, so the throughput drop cannot be attributed to the server alone.

Cold first run (`loadtest_run1.txt`, before the N+1 fix, first traffic after a fresh start — lazy expiry sweeps and bulk "read all" of ~70 % unread seeded notifications): 1.5–7.7 req/s with timeouts at C=32/64. Recorded as found; the warm runs above are after the fix and a 20 s warm-up.

Interpretation: saturation at ≈ 60 req/s for this mix on 2 shared vCPUs, CPU-bound (server ≈ 1.3 cores, the rest to Postgres and the generator). Expectations differ by environment: **dev** (this sandbox) — numbers above; **stress** — latency grows linearly past C≈8 with no errors up to C=64 (no SSE) — no crash, no 5xx; **production** — not measured; size by running the same script against the target hardware.

## 6. Evaluations (no clinical rules invented)

- **Per-unit shipment reconciliation** — evaluated, **not implemented**. Today a FAILED shipment is reconciled as a whole (`RETURNED_TO_ORIGIN` with every unit code echoed and a storage attestation, or written off); a partial loss must be written off and recovered units re-added (losing unit identity). Per-unit outcomes need a per-item outcome column, partial restock under the shipment lock, an attestation per unit, and UI — a feature with inventory-integrity risk, explicitly out of scope for this round; listed in §8.
- **Plasma post-thaw window** — evaluated, **not implemented**. `clinical_sources.py` cites the frozen FFP shelf life (12 months) and deliberately leaves the post-thaw window unset: modelling it needs a THAWED unit state and a cited, jurisdiction-specific rule. No rule was invented.

## 8. Known limitations (current)

1. Docker, MinIO, CI and real SMTP not executed in this environment (commands above).
2. ClamAV verified with a test signature only; detection breadth depends on freshclam in deployment.
3. Audit guard is bypassable by the table owner; non-owner app role is a deployment step not verified here. Checkpoint store must be append-only to detect removal of its newest lines.
4. Two dev-only npm advisories under Tailwind 3 (no fix without Tailwind 4).
5. Analytics overview remains O(total rows) per call (GROUP BY counts).
6. Per-unit shipment reconciliation and plasma post-thaw modelling: out of scope (§6).
7. Load numbers are from a shared 2-vCPU sandbox; not production capacity.
8. Other per-row list serializers (`/emergencies` mine, `/shipments`, `/certificates`) still issue a few statements per row; bounded by a user's own items and not slow at the measured volumes — not changed.
