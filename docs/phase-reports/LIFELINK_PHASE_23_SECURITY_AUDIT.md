# LifeLink — Phase 23 Security Audit: Adversarial Review

## 0. A factual correction, stated up front

The originating instructions for this phase describe LifeLink as a "Flask" application. This is incorrect, and per this phase's own "do not assume, verify against reality" instruction, it is corrected here rather than carried forward: the backend is **FastAPI** (`from fastapi import FastAPI` in `app/main.py`; `fastapi>=0.111` in `requirements.txt`), built on SQLAlchemy + Alembic + PostgreSQL, with Redis/RQ for background jobs and an optional Neo4j graph engine. Every finding below is evaluated against the real FastAPI/APIRouter/Pydantic architecture — dependency-injected auth (`Depends(get_current_user)`), `Depends(require_roles(...))` role gates, and `Depends(verify_origin)` CSRF checks — not against Flask's request-global/decorator model, which this codebase does not use anywhere.

## 1. Methodology

This audit combined static source review (reading every route file, the auth/session/config core, storage, email, and graph modules in full) with live adversarial testing: real HTTP requests against the real application, wired to a real PostgreSQL database and real Redis, using seeded accounts of every role. No destructive testing was performed against any external system; every probe ran against this repository's own local/test infrastructure (the `lifelink_test` database and a local Redis DB), per this phase's non-negotiable constraint. Every "confirmed" finding below was reproduced with a concrete request/response pair before being written up, and is backed by an automated regression test in `backend/tests/test_phase23_security_hardening.py` and, for the browser-facing behaviors, `frontend/e2e/phase23_security_hardening.spec.ts` — nothing here is asserted from code-reading alone without a passing (or, pre-fix, a failing-as-expected) test to back it.

Terminology, per this phase's own rules: **CONFIRMED** means reproduced with a real request against real application code and a real database row. **NO ISSUE FOUND** means the specific attack surface was checked and the existing protection held. Nothing here is called "secure," "penetration tested," "WAF protected," or "OWASP certified" — those claims would be false for the level of review actually performed (see section 19 of the companion report for the explicit non-claims).

## 2. Endpoint inventory (evidence base)

All 13 route files were read in full and cross-referenced against their Pydantic schemas: `auth.py`, `patients.py`, `donors.py`, `family.py`, `blood_requests.py`, `emergencies.py`, `notifications.py`, `hospitals.py`, `matching.py`, `certificates.py`, `admin.py`, `verifications.py`, `health.py`. Every state-changing route (`POST`/`PUT`/`PATCH`/`DELETE`) was checked for three things: (a) a `Depends(verify_origin)` CSRF guard, (b) a real object-ownership or role check before acting on a path-parameterized resource id, and (c) whether any request field could influence a security-relevant column (`role`, `is_active`, `is_email_verified`, `identity_verified`, `verified`) beyond what its Pydantic schema declares. `auth.py`'s router itself carries `dependencies=[Depends(verify_origin)]` at the router level, so every route in that file is covered without a per-route annotation; every other file annotates `verify_origin` per mutating route. No mutating route was found missing this guard.

## 3. Authentication & session architecture — reviewed, live-tested

Password hashing is Argon2 (`app/core/security.py`); tokens/OTPs are `secrets`-module-generated and never stored raw, only as `sign()` (keyed HMAC-SHA256) digests; comparisons use `hmac.compare_digest`. Sessions are opaque server-side ids in an `HttpOnly` cookie (`app/api/cookies.py`, `app/services/session_service.py`), never a client-decodable JWT. `_load_user_from_request` (`app/api/deps.py`) independently enforces: the session's user still exists and `is_active`; the session predates the user's `password_changed_at` (a password change invalidates every prior session, including the one making the change — a fresh session is issued in the same request); an absolute lifetime cap (`session_absolute_ttl_seconds`, default 90 days) independent of a sliding idle timeout (`session_ttl_seconds`, default 14 days) that resets on each authenticated request.

Live-tested (backend tests 15–18 in the companion test file; browser tests A, G, H): a forged/garbage cookie value is rejected with 401 and does not crash the server on null bytes, SQL-metacharacter strings, or oversized values; `/auth/logout` deletes the server-side session immediately (a replay of the same cookie value afterward gets 401); changing the password issues a new cookie and invalidates the old one immediately (verified by literally replaying the pre-change cookie value from a second client); deactivating a user mid-session (`is_active = False`) makes their very next request fail authentication, with no need to wait for the session to expire. **NO ISSUE FOUND** in any of the above — the existing design already closes these classes of attack; this audit's contribution was proving it, not fixing it.

## 4. CSRF, CORS

`verify_origin` (`app/api/deps.py`) rejects a present `Origin` header that is not in `settings.cors_origin_list`, and passes through an absent `Origin` (non-browser clients cannot be CSRF targets — a browser cannot omit `Origin` on a cross-site request). CORS middleware (`app/main.py`) uses an explicit env-driven origin allowlist, `allow_credentials=True`, and explicit method/header allowlists — no wildcard origin, which would be incompatible with `allow_credentials=True` under the CORS spec regardless. Live-tested (backend test 19–21; browser test F): a forged cross-site `Origin` on a real, authenticated, cookie-carrying `POST /blood-requests` is rejected with 403; the same request with the real frontend origin succeeds; the same request with no `Origin` header at all (simulating a non-browser API client) succeeds. **NO ISSUE FOUND.**

## 5. Security response headers — CONFIRMED gap, FIXED

Before this phase, the backend set none of `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, or `Permissions-Policy` on any response. **Fix applied:** `app/core/security_headers.py`, a lightweight ASGI middleware wired into `app/main.py`, sets `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, and a restrictive `Permissions-Policy` on every response, plus `Strict-Transport-Security` when actually running in production over a Secure cookie configuration (sending HSTS over plain HTTP would be a promise the connection can't back up). **Deliberately not added: a Content-Security-Policy.** The frontend loads OpenStreetMap/Leaflet map tiles and marker imagery from external hosts; enumerating every legitimate external origin the SPA calls is a frontend asset-inventory exercise this backend-focused phase did not perform, and a guessed/wrong CSP would silently break exactly the map UI Phase 22 just finished hardening — the one class of regression this phase's own rules explicitly forbid. This is recorded as a known, deliberate gap (section 18 of the companion report), not a silent omission, and is backed by a test (`test_no_content_security_policy_is_shipped_yet_documented_gap`) that will fail loudly the moment someone adds a CSP without updating it.

## 6. Authorization / RBAC / IDOR — live adversarial testing

`require_roles(*roles)` (`app/api/deps.py`) reads `user.role` from the DB row resolved by the session — never from any client-supplied field — and audits every denial (`authz.role_denied`). Object-level authorization is implemented per-resource with explicit `_can_view`/`_can_manage` helper functions in `blood_requests.py`, `emergencies.py`, `family.py`, and inline ownership checks elsewhere (`certificates.py`, `donors.py` appointments, `notifications.py`).

Live-tested, each reproduced with two real seeded accounts and audited via a real `AuditLog` row query (not just the HTTP status code):
- A patient cannot view, cancel, or fulfill another patient's blood request (404, `blood_request.access_denied` audited).
- A patient cannot view or cancel another patient's emergency, including via a FAMILY account with no accepted link to that patient (404, `emergency.access_denied` audited).
- A donor cannot view another donor's certificate, nor download it without either ownership or a valid signed token (404 / 401, `certificate.access_denied` audited).
- A donor cannot cancel another donor's appointment (404, `donor_appointment.access_denied` audited).
- A patient cannot mark another patient's notification read (404).
- A FAMILY account that is not the patient on a link cannot accept/reject it, and an outsider cannot revoke a link they're not party to (403, `family_link.access_denied` audited).
- A hospital cannot query or select a resource pathway using another hospital's facility id (403, `hospital.facility_access_denied` audited) — this closes the one genuinely two-sided ("hospital A vs. hospital B") case the existing Phase 8 authorization test suite didn't already cover for this specific pair of routes.
- Every one of `/admin/*`'s admin-only endpoints rejects every non-admin role (403, `authz.role_denied` audited), confirmed across all four self-registerable roles.
- A DONOR-role account cannot create an emergency (PATIENT/FAMILY/HOSPITAL only); a non-DONOR account cannot respond to a blood request.

**NO ISSUE FOUND** beyond the one genuinely new gap below — the existing authorization architecture (ownership checks + role gates + audit-on-denial) was, on adversarial testing, already correctly enforced everywhere it was probed.

## 7. Privilege escalation & mass assignment — CONFIRMED gaps checked, NO ISSUE FOUND

Self-registration (`POST /auth/register`) validates `role` against `REGISTERABLE_ROLES = {PATIENT, FAMILY, DONOR, HOSPITAL}` at the schema level (`RegisterIn._role_is_self_registerable`) — `role: "ADMIN"` is rejected with 422 before it ever reaches a database write. `is_email_verified` and `is_active` are never read from client input in `auth_service.register`; they're hardcoded server-side. Every profile-update endpoint (`PUT /donors/me`, `PUT /patients/me`, `PUT /hospitals/me`) applies only the fields present on its own narrow Pydantic `*Update` schema via `payload.model_dump(exclude_unset=True)` — `DonorProfileUpdate` has no `identity_verified` field at all, so a client sending `{"identity_verified": true, "role": "ADMIN"}` alongside legitimate fields has those two silently ignored (confirmed live: the response and a follow-up `GET` both show the flag unchanged). The only code path that ever sets `DonorProfile.identity_verified` or `HospitalProfile.verified` to `True` is `verifications._apply_approval`, reachable only through `POST /admin/verifications/{id}/approve` behind `require_roles(ADMIN)`. **NO ISSUE FOUND.**

## 8. Rate limiting & idempotency abuse — CONFIRMED gap, FIXED

**Confirmed finding (fixed):** `POST /emergencies` and `POST /blood-requests` had **no rate limit at all**, unlike every other state-changing endpoint in the application (registration, login, password reset, verification submission, and family-link requests all had one). Both endpoints trigger a real donor/hospital notification fan-out (in-app + email, and SMS where MSG91 is configured) on every genuinely distinct creation — an unbounded account could therefore be used to flood every compatible donor's device with "EMERGENCY" pushes at no cost to the caller, which is precisely the kind of resource-exhaustion/notification-spam vector this phase's rate-limiting section calls out. **Fix applied:** `enforce_rate_limit("emergency_create:account", ...)` and `enforce_rate_limit("blood_request_create:account", ...)`, both placed *after* the existing idempotency-key replay/conflict handling so that retrying the exact same submission (a double-click, a network retry) never itself counts against the limit — only genuinely distinct creations do. The limits (10 emergencies / 10 minutes; 20 blood requests / hour, per account) are deliberately generous, per this phase's explicit instruction that "emergency workflows require special care" and must not be broken by an arbitrary cap: a real crisis can reasonably involve several distinct broadcasts (a patient and more than one family member acting on their behalf, a location change, a hospital raising it for several patients) comfortably within these limits, while a scripted spam loop is not. Live-tested (backend tests 22–23; browser test I): the limit does trip with a real 429 + `Retry-After` after the configured count, and idempotent replay of the identical payload+key never trips it even across many more iterations than the limit.

Idempotency-abuse edge cases were also live-tested for both resources: same-user/same-key/same-payload replays the original result (200, not a duplicate row); same-user/same-key/**different**-payload is rejected with 409 for blood requests (the stricter, documented Phase 19 behavior) and safely replays the original for emergencies (the simpler, documented Phase 12 behavior — this asymmetry between the two resources is a pre-existing, deliberate design choice, not an inconsistency this audit introduced); two different users using the identical key string create two independent rows, confirming the key is scoped per-actor, not global. A direct count query against the database (not just the HTTP response) confirmed exactly one row exists after a replay, ruling out a race where the API response lied about deduplication while a second row was silently created. **NO ISSUE FOUND** in the idempotency mechanism itself.

## 9. Donation-ownership gap — CONFIRMED, FIXED

**Confirmed finding (fixed):** `POST /donors/me/donations` accepted any `blood_request_id` a donor supplied, with no check that the donor had ever actually responded to — let alone been accepted on — that specific request. A donor could attach an arbitrary, unrelated blood request (someone else's, in a different city, of a different blood type) to their own self-reported donation history, corrupting the record `certificates.py`'s `issue_certificate` and the request's own `fulfill_request` logic both treat as ground truth for who actually helped with what. **Fix applied:** when `blood_request_id` is supplied, the endpoint now requires a real `DonorResponse` row for that exact (request, donor) pair with `status == ACCEPTED` before allowing the reference; a donation with no request reference at all (the legitimate "off-platform donation" case the field was always optional for) is unaffected. Live-tested (backend tests 27; browser test L): an unrelated donor is rejected with 400; a donor who genuinely accepted the request succeeds with 201; an off-platform donation with `blood_request_id: null` still succeeds with 201.

## 10. Email/notification channel — CONFIRMED HTML-injection gap, FIXED

**Confirmed finding (fixed):** `app/services/email_service.py` built every outbound HTML email via raw Python f-strings, interpolating user-controlled free text — `full_name` (editable by any account holder), and notification `title`/`body` (which frequently echo a *different* user's free text: an emergency's `location_text`, a blood request's `note`, a family member's display name in a notification body) — with **zero HTML escaping**. A crafted name or note containing `<img src=x onerror=...>` or a fake `<a href="...">` would render as live, executable markup in any HTML-capable mail client the *recipient* (not the attacker) uses — a genuine stored-HTML-injection vector, confirmed by tracing concrete attacker-controlled sinks into `send_notification_email`/`send_verification_email`/`send_password_reset_otp` from call sites in `emergencies.py`, `hospitals.py`, `blood_requests.py`, `verifications.py`, `donors.py`, and `family.py`. The frontend's own React rendering of the same data was separately confirmed unaffected (React escapes text content by default; no `dangerouslySetInnerHTML` was found rendering any of these same fields) — this is a vulnerability specific to the email channel, not the web app. **Fix applied:** every interpolated user-controlled value in `email_service.py`'s three template functions is now wrapped in `html.escape()` before interpolation; server-generated values that need no escaping (the verification link built from server config + a URL-safe token, and the six-digit numeric OTP) are left as-is, since escaping them would change nothing and the comment at each call site says why. Live-tested (backend tests 28): a hostile `<img onerror=...>` full name, a `<script>`-bearing notification title, an `<a href="javascript:...">`-bearing body, and a hostile verification-email name are all confirmed to appear only as inert, escaped text (`&lt;img ...&gt;`) in the captured outbound email, never as a live tag; the OTP and verification link remain intact and unescaped.

## 11. Injection surface sweep — NO ISSUE FOUND

SQL: every database access in this codebase goes through SQLAlchemy's ORM/Core query builder (`select(...)`, `.where(...)`) with bound parameters; no raw SQL string concatenation of user input was found anywhere. Cypher (Neo4j): `app/core/graph.py`/`app/services/graph_service.py` parameterize every query via `session.run(query, **kwargs)` — no string interpolation of user input into Cypher text. Command injection: no `subprocess`/`os.system`/`os.popen` call anywhere in the application code takes user-controlled input (the only subprocess-adjacent code is tooling/scripts, not request-handling paths). SSRF: no route accepts a user-supplied URL that the backend then fetches server-side. Open redirects: no route performs an HTTP redirect to a user-supplied URL. Frontend XSS: no `dangerouslySetInnerHTML` (or equivalent) was found rendering user-controlled data anywhere in the React frontend; all user-controlled display data is rendered as ordinary React text content, which is escaped by default.

## 12. File & object storage — NO ISSUE FOUND (re-confirms Phase 14/17/20), one CONFIRMED gap fixed separately (§13)

Verification-document upload (`verifications.py`) sniffs the real file bytes (`_sniff_content_type`) and requires them to match the client-declared `Content-Type`, independent of the (attacker-controlled) multipart header — live-tested with an HTML payload declared as `application/pdf`, correctly rejected with 422. Filenames are sanitized (`_safe_filename`) to `[A-Za-z0-9._-]` only, and the actual storage key is always an app-generated `uuid4().hex`-prefixed path, never derived from the client-supplied name — a `../../etc/passwd`-style filename cannot escape the storage prefix regardless. Uploads are read in bounded 64 KB chunks with an early abort once the configured size cap is exceeded (`_read_bounded`), so an oversized upload cannot be fully buffered into memory before being rejected. Certificate and verification-document downloads are marked `Cache-Control: private, no-store` and are authorized per-request (ownership, admin, or a signed, TTL-bound, per-resource-id HMAC download token for certificates) rather than trusting a bare object key. **NO ISSUE FOUND** in any of the above on this pass — all were re-verified, not assumed from prior phases' reports.

## 13. Secrets & configuration — CONFIRMED gap, FIXED

**Confirmed finding (fixed):** `Settings.secret_key` defaults to the literal, source-visible string `"dev-insecure-secret-change-me"`, and — before this phase — nothing prevented the application from booting in `ENVIRONMENT=production` with that exact default still in place. `secret_key` is the sole key behind `app.core.security.sign()`, which is what protects stored email-verification tokens and password-reset OTPs at rest (only `sign(value)` is ever persisted, never the raw value) and behind `certificate_service.make_download_token`/`check_download_token`'s per-certificate HMAC download tokens. A production deployment that never overrode this setting would have every one of those HMACs forgeable by anyone who can read this repository's source — which is a real, previously-documented-but-unremediated gap (`LIFELINK_PHASE_0_AUDIT.md` §12, rated High at the time and never fixed). **Fix applied:** a new `_validate_secret_key` model-validator in `app/core/config.py`, mirroring the existing `_validate_cookie_security` fail-closed pattern in the same file, raises at settings-construction time (i.e., at process boot) when `environment == "production"` and `secret_key` still equals the shipped default — refusing to start rather than silently running insecurely. Non-production environments (development, test) are unaffected, matching every real developer's local no-`.env` bootstrap. Live-tested (backend tests 29): constructing `Settings(environment="production", secret_key=<default>)` raises `ValueError` naming `SECRET_KEY`; the identical construction with a real custom value succeeds; the default is still accepted in `development`; and `sign()` is confirmed to actually depend on `secret_key` (changing the key changes the digest for the same input), closing the loop between "the setting is guarded" and "the setting is what actually matters."

No other secrets (API keys, credentials, private keys) were found committed to the repository; `.gitignore`/`.env.example` were checked and contain no real credentials, only placeholder/example values. `requirements.txt` pins reasonably current major versions of FastAPI/SQLAlchemy/Argon2/boto3 with no known-vulnerable pin identified during this review (no live CVE database lookup was performed as part of this pass — see the companion report's known-gaps section).

## 14. Audit log integrity — NO ISSUE FOUND

Every access-denial class exercised in section 6 was independently confirmed to leave a real, queryable `AuditLog` row — not merely the correct HTTP status code — by querying the database directly after each probe (`db_session.scalars(select(AuditLog).where(...))`), for `authz.role_denied`, `blood_request.access_denied`, `emergency.access_denied`, `certificate.access_denied`, `donor_appointment.access_denied`, `family_link.access_denied`, and `hospital.facility_access_denied`. Each denial record carries the actor's real user id, the attempted action, and (for role denials) the actor's actual role and the route's required roles — enough to reconstruct what was attempted after the fact, which is the practical test of "audit log integrity" this phase's own language calls for.

## 15. Enumeration resistance — NO ISSUE FOUND

`POST /family/links` returns the identical 404 response body for "no account exists with this email" and "an account exists but has been suspended (`is_active=False`)" — confirmed with a byte-for-byte comparison of both response bodies in a live test — so a FAMILY caller cannot use this endpoint to learn which registered patient emails have since been suspended, closing the narrow enumeration signal this phase's rules flag.

## 16. Concurrency / race conditions — reviewed, NO NEW ISSUE FOUND

Every "first responder wins" write path already reviewed and fixed in prior phases (blood-request/emergency idempotent creation, donor/emergency-responder first-response, family-link creation, verification approve/reject) uses either `SELECT ... FOR UPDATE` row locking or a `SAVEPOINT`-guarded insert with a unique-constraint-triggered fallback read, so two near-simultaneous requests for the same resource cannot both "win." This phase's own two new rate-limited/ownership-checked endpoints (`create_emergency`, `create_request`, `log_donation`) do not introduce any new multi-step check-then-act sequence that wasn't already covered by this pattern — the new checks (rate limit, donation ownership) are single atomic reads with no intervening write, so they don't create a new race window. No new concurrency defect was introduced or found.

## 17. What was explicitly checked and found already correct (not re-litigated as "findings")

Per this phase's own instruction not to manufacture issues where none exist: CORS configuration, the CSRF (`verify_origin`) mechanism and its coverage, the session/password architecture, SQL/Cypher/command injection surfaces, SSRF, open redirects, frontend XSS via React rendering, mass-assignment protection on every profile-update endpoint, the verification-approval authorization boundary, file-upload magic-byte sniffing and filename sanitization, bounded upload reads, signed certificate download tokens, and audit-log coverage of every denial path were all reviewed and — beyond the five confirmed-and-fixed items in sections 5, 8, 9, 10, and 13 — found to already be correctly implemented. This audit's job on those fronts was verification, not remediation.

## 18. Non-fabrication statement

This audit makes no claim that LifeLink is "secure," "penetration tested" in the professional sense, "WAF protected," or "OWASP certified" — none of those would be true statements for the review actually performed here (adversarial code review plus live functional/API-level testing against a local, controlled environment, not a licensed penetration test, a deployed WAF, or a formal OWASP ASVS certification process). Every "CONFIRMED" finding in this document is backed by a reproducible test in the repository; nothing is asserted from inference alone. Section 18 ("known remaining gaps") of the companion `LIFELINK_PHASE_23_SECURITY_REPORT.md` lists, explicitly, what this pass did not cover.
