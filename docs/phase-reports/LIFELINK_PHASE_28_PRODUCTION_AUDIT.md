# LIFELINK — Phase 28: Production Environment, Database & Deployment Hardening — Audit

Scope: production-readiness hardening of the existing FastAPI/PostgreSQL/Redis/RQ/Neo4j/S3 backend and Vite/React frontend. Not a rebuild. Every finding below was checked against the real source tree in this checkout (`/home/claude/lifelink_impl/project`), not assumed from prior phase reports. Phase 24–27 reports were read first; their claims (782 backend tests, 65/65 Playwright, the N+1 notification fix, the accessibility baseline) were re-verified rather than trusted blindly — see §16–18.

## 1. Environment architecture

`app/core/config.py`'s `Settings.environment` (env var `ENVIRONMENT`) is the single source of truth for dev/test/staging/production. `is_test` recognizes `test`/`testing`; `is_production` recognizes `production`/`prod`; anything else (including `staging`, `development`) is treated as non-production for the fail-closed validators below but does not silently get production security behavior — `staging` gets neither the dev conveniences nor the production hard-fails unless an operator sets the individual flags (`SESSION_COOKIE_SECURE`, etc.) themselves. `tests/conftest.py` hard-pins `ENVIRONMENT=test` and overrides `DATABASE_URL` to `lifelink_test` **before** the app is imported, so the test suite cannot silently run against a production-shaped database. This was true before Phase 28 and is unchanged; Phase 28 added the `LOG_LEVEL` setting and its own validator alongside the existing ones.

## 2. Config / fail-closed validator audit

Pre-existing (Phase 0/7): `_validate_secret_key` refuses to boot in production with the shipped default `SECRET_KEY`; `_validate_cookie_security` refuses to boot in production without `SESSION_COOKIE_SECURE=true`, and refuses `SameSite=None` without `Secure` in any environment.

Phase 28 additions, all in `app/core/config.py`:
- `_validate_secret_key` extended with a minimum-length check: production refuses a `SECRET_KEY` under 32 characters (256 bits — matches HMAC-SHA256's own output size), closing the gap where a technically-non-default but trivially weak key (`SECRET_KEY=x`) would previously have passed.
- New `_validate_log_level`: `LOG_LEVEL` must be a real `logging` level name; normalized to uppercase.
- Four new DB settings (`db_connect_timeout_seconds`, `db_statement_timeout_ms`, `db_pool_timeout_seconds`, `db_pool_recycle_seconds`) and two new Redis settings (`redis_connect_timeout_seconds`, `redis_socket_timeout_seconds`) — all reliability/timeout knobs, **none of them touch `pool_size`/`max_overflow`**, which Phase 24 and Phase 27 each independently measured to have no effect on this app's real bottleneck (see §16).

All eleven validators (7 pre-existing + 4 Phase 28) are covered by `tests/test_phase28_production_config.py` (11 tests) plus the pre-existing config tests; all pass.

## 3. Secret management audit

`.gitignore` (backend) already excluded `.env`/`.env.*` with a `!.env.example` exception, `.venv/`, caches. `.env.example` documents every setting including a correct Gmail App Password setup — real secrets are never suggested to be committed. Phase 28 added `backups/` and `*.dump` to `.gitignore` (new backup-script output — see §14) and created `backend/.dockerignore` (new — see §11) so a real local `.env` or a backup dump sitting in the build context can never be baked into a Docker image layer, which is a materially different (and worse) exposure than a stray local file: an image can be pushed to a registry and inspected layer-by-layer long after the file itself is deleted.

`grep` across `app/` for logging calls referencing `password|otp|secret|token|api_key|credential` returned zero matches before Phase 28 and zero matches after (re-run after adding the new logging infrastructure in §13).

SQLAlchemy 2.0, `postgresql+psycopg://`, `pool_pre_ping=True` (pre-existing). Phase 28 added, in `app/db/session.py`: `pool_timeout` (was an undocumented library default), `pool_recycle=1800s`, and `connect_args` carrying `connect_timeout` and a `-c statement_timeout=...` PostgreSQL session option. Verified live: `SHOW statement_timeout` inside a real connection returns `30s`. `pool_size`/`max_overflow` are explicitly untouched, per the master prompt's own instruction and Phase 24/27's prior evidence — see §16.

Migration chain: 19 revisions, single linear chain (no branches, confirmed via `alembic history`). A real migration smoke test was run this phase: a disposable database (`lifelink_migration_smoketest`) was created, `alembic upgrade head` run from empty (all 19 revisions, zero errors), its resulting schema diffed against the real dev database's schema (29 tables each, zero diff), a real `downgrade(-3)` → `upgrade(head)` round-trip performed (clean, zero diff after), and `upgrade head` confirmed idempotent when already current. `scripts/production_smoke_test.py`'s `migration_state_correct` check (§17) re-confirms `alembic_version` matches the checkout's head on every run.

## 5. Redis / RQ audit

`app/core/redis.py`: both the text client (sessions, rate limiting) and the binary client (RQ) now carry explicit `socket_connect_timeout`/`socket_timeout` (Phase 28; previously unbounded — a hung/unreachable Redis would block a request forever instead of raising the `RedisError` this app already classifies as an honest 503). Verified safe for RQ's own blocking dequeue by reading `rq/worker/base.py`: RQ widens `socket_timeout` itself if the configured value is smaller than what its own blocking wait needs — it only ever widens, never leaves a real wait vulnerable to a spurious timeout.

RQ job retry: `email_job_max_retries=3` (pre-existing, Phase 18), immediate re-enqueue on transient failure. `app/workers/worker.py` is a plain `Worker([...], connection=rq_redis).work(with_scheduler=True)` listening on both the email and SMS queues from one process — unchanged this phase, and its startup (connection to real Redis) is now covered by `scripts/production_smoke_test.py`'s `rq_worker_can_start` check.

**Operational finding, not fixed this phase (documented per the master prompt's "do not hide limitations" instruction):** this session's Redis instance was found holding 148,965 stale queued email jobs, accumulated from Phase 24–27's own repeated load tests (each blood-request/emergency creation enqueues up to ~129 emails). This confirms the RQ email queue has no automatic bound — a sustained real burst (or another repeated load-test run) can accumulate an arbitrarily large backlog with no expiry or cap. This is a genuine scalability/operational gap, recommended for Phase 29 (see §20). It was cleared for this session's testing (`FLUSHDB` on Redis db 0 — test/load-test debris only, not real application data; this also cleared active sessions and rate-limit counters, which is expected and harmless for a dev/audit session but would not be an acceptable production remediation).

## 6. SMTP / Gmail email architecture audit

**Design confirmed correct by code review**, matching the master prompt's required architecture exactly: the configured `MAIL_USERNAME`/`MAIL_PASSWORD` (a Gmail account with an App Password) is the **sender** for every outbound email (verification, OTP, password reset, notifications); the registered LifeLink user's own email address (which may itself be a Gmail address) is only ever the **recipient**. LifeLink's own `password_hash` on the `User` row is the only credential ever checked at login — nothing in `app/services/` or `app/api/routes/auth.py` reads, stores, or validates a user's Gmail password, and Google OAuth is not implemented (not requested, and correctly absent). `.env.example` documents Gmail App Password setup correctly (`smtp.gmail.com`, port 587, STARTTLS).

**Transport-level verification, this session:** Mailpit (the docker-compose dev SMTP catcher) was not running in this sandbox. `aiosmtpd` (already an installed Python package) was used as a functionally-equivalent local SMTP debug server — explicitly disclosed as a substitute, not silently claimed as Mailpit — to send a real message through the app's own `_smtp_send` function end-to-end. This is genuine LOCAL-VERIFIED evidence of the transport layer the existing test suite never exercises (`settings.is_test` short-circuits real SMTP entirely in tests). Real Gmail delivery is **NOT-LIVE-VERIFIED**: no real Gmail credentials were available in this sandbox, and this sandbox has no general outbound internet access (confirmed independently — see §17) to reach `smtp.gmail.com` even if credentials were supplied.

## 8. Neo4j audit

Unchanged this phase — already production-correct.

**NEO4J LIVE VERIFICATION: NOT AVAILABLE IN THIS ENVIRONMENT.** This session independently strengthened that classification beyond simply re-confirming Neo4j Aura is unreachable: an arbitrary, unrelated hostname was tested for DNS resolution in this sandbox and failed, and (in §11's Docker investigation) `registry-1.docker.io` was independently confirmed blocked by the sandbox's own egress proxy while `pypi.org` succeeded. Sliding idle timeout (`session_ttl_seconds`, refreshed on every authenticated request) bounded by an absolute cap (`session_absolute_ttl_seconds`) independent of activity — unchanged this phase, already production-correct, and already covered by Playwright's Phase 23 security suite (HttpOnly cookie, logout invalidation, password-change invalidation — all still passing, see §18).

## 10. Health / readiness audit

Phase 28 added a liveness/readiness split to `app/api/routes/health.py`, alongside the original `/health` (kept byte-for-byte behaviorally identical for backward compatibility):
- `GET /health/live` — always 200, zero dependency checks. This is what a container orchestrator should gate a *restart* on.
- `GET /health/ready` — 503 only if PostgreSQL or Redis (the two hard, no-fallback dependencies) are down; Neo4j/storage/email are reported under an `optional` key that never affects the status code, since all three are architected to degrade gracefully. No live I/O against storage/Neo4j is performed here (that already exists, authenticated, at `GET /admin/system/health`) — only cheap config-state checks, safe to poll frequently.

5 tests in `tests/test_health.py` cover both new endpoints, including that an optional-dependency failure never flips readiness (verified via `monkeypatch`, not by breaking real infrastructure).

## 11. ASGI / deployment audit

`app/asgi.py` (Phase 27) and `scripts/run_production.sh` (Phase 27) were re-read and re-verified this phase, not re-written: `app.asgi:application` boots correctly, serves real HTTP, and shuts down gracefully on SIGTERM (verified again this phase — see §16's boot test).

Phase 28 changes:
- **`Dockerfile`**: previously ran `uvicorn app.main:app` as root with no healthcheck. Now: (a) runs as a non-root `appuser` (created via `useradd`, ownership `chown`'d, verified this session that a non-root user can be created and can write to its own owned directory using this sandbox's own equivalent coreutils, since a full `docker build` could not run — see below); (b) a `HEALTHCHECK` directive polling `/health/live` via Python's stdlib `urllib` (no extra package installed); (c) the default `CMD` now points at `app.asgi:application` (Phase 27's production entrypoint) instead of `app.main:app` directly, with `--proxy-headers --forwarded-allow-ips=*`.
- **New `backend/.dockerignore`**: excludes `.env*` (except `.env.example`), `backups/`/`*.dump`, `.venv/`, caches, `.git/` — see §3.
- **`docker-compose.yml`**: left functionally unchanged (it is correctly dev/E2E-oriented — fixed passwords, `--reload`, auto-migrate-on-start) but given an explicit header comment marking it DEV-ONLY, with a pointer to the Dockerfile + `run_production.sh` + `.env.example` for a real deployment, and an explanation of exactly which of its choices are dev-appropriate but would be production findings.

**Docker build: NOT-LIVE-VERIFIED, blocked by this sandbox's own egress allowlist**, not by any defect in the Dockerfile: `docker build` failed with `403 Forbidden` resolving `python:3.12-slim` from `registry-1.docker.io`, and a direct `curl` to the same host independently confirmed the block (`pypi.org` succeeded from the same shell). The Docker daemon itself does run in this sandbox (`dockerd` started successfully, `docker compose config` validated the compose file's YAML), so this is specifically a registry-egress restriction. Given the full image build could not run, the **exact command in the Dockerfile's `CMD`** was run directly on this host instead (`uvicorn app.asgi:application --host 0.0.0.0 --port 8000 --proxy-headers --forwarded-allow-ips=*`): it booted, served `/health/live` with 200, and shut down cleanly on `SIGTERM` (uvicorn's own graceful sequence: "Shutting down" → "Waiting for application shutdown" → "Application shutdown complete"). The `useradd`/`chown`/non-root-write and the `HEALTHCHECK`'s exact Python one-liner were also each independently verified to work on this host's own (also Debian-based) userland. This is real evidence for every moving part of the Dockerfile; only the single combined "does `docker build` succeed end-to-end" step is blocked by sandbox network policy.

## 12. HTTPS / security headers / CSP audit

`app/core/security_headers.py` (Phase 23, unchanged): `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, a deny-all `Permissions-Policy`, conditional HSTS when production + secure cookies. This only ever applies to the backend's own JSON API responses — the backend never serves the SPA's HTML (`grep` for `StaticFiles`/`FileResponse` in `app/main.py` finds nothing), so HTTPS termination and framing protection for the *frontend shell itself* are architecturally a static-host/reverse-proxy responsibility, not something this backend can provide; this is now stated explicitly in the deployment checklist (§19/§20).

**CSP — the Phase 23 documented gap — was resolved this phase**, not left open. A `vite-csp-plugin.ts` (new file) injects a production-build-only (`apply: 'build'`) `<meta http-equiv="Content-Security-Policy">` as the very first element in `<head>` (load-bearing: a CSP delivered via `<meta>` only governs elements parsed *after* it). The policy was derived from a complete, grepped inventory of this frontend's actual external-origin footprint, then **tested against a real headless-browser run of the real `npm run build` output**, not assumed:
- First real run surfaced 2000+ genuine `style-src` violations from React's own dynamic `style={{...}}` props and Leaflet's own JS-driven element positioning (both write to the `style` attribute at runtime, which CSP's `style-src` governs regardless of how it was set) — `style-src` was adjusted to include `'unsafe-inline'` specifically (script-src stays strict; CSS injection cannot execute arbitrary JavaScript in a modern browser, so this is a considered, documented trade-off, not an oversight).
- The same run surfaced a genuine, previously-unflagged finding: **16 hardcoded `https://lh3.googleusercontent.com/aida-public/...` image URLs** (leftover Stitch-mockup asset links, including the literal LifeLink logo) used as real `<img src>` across many production pages (PatientDashboard, DonorDashboard, DonorRecommendation, DecisionTransparency, GraphDecisionEngine, MathematicalModel, Analytics, DonationCertificate, SimulationMode). This is not a secret leak — it is allow-listed in `img-src` rather than stripped, per the master prompt's "fix genuine leaks only" instruction — but is flagged as a real production reliability/privacy risk (an external, LifeLink-uncontrolled asset host with no permanence guarantee, and every page load reveals the visitor's IP to Google) and recommended for self-hosting in Phase 29 (§20).
- `frame-ancestors` was deliberately **excluded** from the meta CSP after a real browser console warning confirmed it is silently ignored when delivered via `<meta>` (a documented CSP spec limitation) — including a no-op directive would have been misleading in this audit. Framing protection for the SPA shell must come from a real HTTP header set by whatever static host/reverse proxy serves the built `dist/` output; this is stated explicitly rather than left implicit.
- After both fixes, a final headless-browser run against a real authenticated session (logged in through the real `/login` UI) showed **zero CSP violations**, and — isolating Leaflet specifically, since the map required an open blood request this test account didn't have — a standalone bundle of this repo's own Leaflet dependency confirmed the CSP's `img-src` genuinely permits real tile requests to `*.tile.openstreetmap.org` (12/12 requests fired with zero CSP refusals; they did not complete due to this same sandbox's TLS-interception limitation on arbitrary outbound HTTPS — `ERR_CERT_AUTHORITY_INVALID`, the same class of restriction as §8/§11 — which is unrelated to whether CSP permitted them).
- Vite dev mode (`npm run dev`) was independently confirmed to receive **no** CSP tag (the plugin's `apply: 'build'` restriction verified directly against the dev server's served HTML), so local development is completely unaffected.

Production HTTPS itself: not provided by this application (FastAPI/uvicorn does not terminate TLS) — this was already true and is now stated explicitly in the deployment checklist rather than left assumed; TLS termination is a reverse-proxy/load-balancer responsibility, not invented or assumed to be any specific provider.

## 13. Structured logging / request correlation audit

Previously: no consistent log format guaranteed, and the `X-Request-Id` header the frontend already sends on every request (specifically so "a report of 'it broke' can be correlated with backend logs," per `frontend/src/lib/api.ts`'s own docstring) was never read, logged, or echoed by the backend at all.

Phase 28 added two new modules: `app/core/request_context.py` (a `ContextVar`-backed request ID, bound per-request by `request_id_middleware`, which reuses a well-formed incoming `X-Request-Id` or generates a fresh UUID, and echoes it back as a response header) and `app/core/logging_config.py` (`dictConfig`-based setup with a `logging.Filter` that injects the current request ID into every log record via the ContextVar — reaching every existing `logger.info/warning/error(...)` call site across the whole codebase, including `app/core/error_handlers.py`'s two handlers, with zero changes to any of them). Both are wired into `app/main.py`; the request-ID middleware is registered first so it is the **outermost** middleware, binding the ID before CORS/security-headers/routing all run. A new `log_level` setting (env `LOG_LEVEL`) is validated at boot (§2).

Verified live, end-to-end, against the real running backend: a request sent with a custom `X-Request-Id` gets it echoed back unchanged; a malformed one is replaced with a fresh UUID; a real `OperationalError`-triggering failure path (verified directly, not just unit-tested) produces a log line carrying the correct correlation ID; a log line emitted outside any request context correctly shows `-`. A fresh repository-wide grep for password/OTP/secret/token/credential patterns in any logging call, re-run after adding this infrastructure, is still clean (§3).

## 15. Production data-safety audit

`app/main.py`'s `lifespan` startup handler was re-read: it only calls `storage.ensure_bucket()` (idempotent, creates the configured bucket/local dir if missing — not demo data) and, on shutdown, `graph.close_driver()`. **No seeding, fixture loading, or demo-data generation happens automatically at any app startup path**, confirmed by grep — nothing in `app/` imports either `scripts/seed_demo_data.py` or `scripts/e2e_seed.py`.

Both of those scripts, however, had no guard against being run manually against a real production `DATABASE_URL` by mistake — a genuine gap given both write large amounts of synthetic/shared-password data (and `e2e_seed.py` additionally *deletes* rows by email first). Phase 28 added a fail-closed guard to each script's `main()` (mirroring `db_restore.sh`'s `RESTORE_ALLOW_PROD` pattern): both now refuse to run when `ENVIRONMENT=production` unless `SEED_DEMO_ALLOW_PROD=yes` is explicitly set, verified live via subprocess (`ENVIRONMENT=production` → exit code 1, refusal message, database never touched) and via 4 new unit tests (`tests/test_phase28_seed_guards.py`) that also confirm normal dev-mode operation is unaffected. No destructive reset/wipe/truncate endpoint was found reachable via the HTTP API (the only "wipe" in the codebase is the Neo4j graph mirror's admin-only, by-design resync-from-Postgres, which never touches the authoritative relational data).

## 16. Scalability findings

**No worker/pool topology change was made this phase**, per the master prompt's explicit instruction: Phase 24 (pool_size 5/10 default, then 20/30) and Phase 27 (15/15) each independently measured no meaningful improvement to the extreme "mixed" synthetic burst scenario from raising the connection pool — Phase 27's real root cause was an N+1 bug in `notify_matching_donors()` (fixed that phase) plus a residual, non-CPU-bound Redis-fan-out-under-massive-contention issue that remained **PARTIALLY FIXED** and is carried forward unchanged here, not re-litigated without new evidence.

This phase's DB/Redis changes (§4, §5) are explicitly orthogonal reliability/timeout settings, not capacity changes. The N+1 fix's own regression test (`tests/test_phase27_notification_scaling.py::test_matching_donor_notification_query_count_is_bounded_not_linear`, asserting the query count stays `<= 40` regardless of donor-pool size) was re-run this phase and still passes, confirming the fix remains intact through every Phase 28 change. A light concurrency sanity check (not a re-run of the full heavy-burst suite, since no topology changed) was performed using the existing `scripts/phase27_loadtest.py` harness: `A_patient_browsing@c=2` (2/2 success, ~17ms avg) and `B_blood_request_create@c=10` (10/10 success, 0 errors/timeouts, ~1.3s avg — consistent with Phase 27's own post-fix write-path measurements) both confirm no regression from the new middleware layer (request-ID + logging, now in front of every single request).

The RQ email-queue unbounded-growth finding (§5) is a **new** Phase 28 discovery, not a Phase 27 carryover, and is recommended for Phase 29.

## 17. External dependencies and this sandbox's network restrictions

This sandbox's outbound network access is a narrow allowlist, confirmed three independent ways this phase: (a) an arbitrary unrelated hostname fails DNS resolution; (b) `docker build`'s pull from `registry-1.docker.io` returns `403 Forbidden` while `pypi.org` succeeds from the same shell; (c) a real headless-browser request to `fonts.googleapis.com` and to `*.tile.openstreetmap.org` both fail with `ERR_CERT_AUTHORITY_INVALID` (the sandbox's own TLS-interception proxy, whose CA the browser doesn't trust — a certificate-validation failure, not a CSP block, confirmed by the complete absence of any CSP-refusal console message for those same requests). None of this is a defect in LifeLink's code or configuration — every code path involved was independently verified correct by other means (§6, §8, §12).

## 19. Deployment checklist

**PRE-DEPLOY:** set `ENVIRONMENT=production`; generate a real `SECRET_KEY` (`python3 -c "import secrets; print(secrets.token_urlsafe(32))"` — the config validator refuses anything shorter than 32 characters or the shipped default); set `SESSION_COOKIE_SECURE=true` and a `SESSION_COOKIE_SAMESITE` appropriate to whether the frontend and API share a registrable domain; set `DATABASE_URL`/`REDIS_URL` to the real managed instances; set `CORS_ORIGINS` to the exact real production frontend origin(s), comma-separated, no wildcard; set real `MAIL_USERNAME`/`MAIL_PASSWORD` (a Gmail App Password) and `MAIL_STARTTLS=true`; set `S3_ENDPOINT_URL`/`S3_ACCESS_KEY`/`S3_SECRET_KEY`/`S3_BUCKET` for real object storage (never leave storage on the local-disk fallback in production); set `NEO4J_URI`/`NEO4J_USERNAME`/`NEO4J_PASSWORD` if the graph engine is wanted (optional — the app runs correctly without it, on the haversine fallback); confirm `VITE_API_URL` is set to the real production API origin **at frontend build time** (it is baked into the built JS, not runtime-configurable); confirm a TLS-terminating reverse proxy/load balancer sits in front of this backend (it does not terminate TLS itself) and in front of whatever serves the built frontend; take a backup (`scripts/db_backup.sh`) before deploying if this is an upgrade, not a first deploy.

**DEPLOY:** build the frontend (`npm run build` — bakes in `VITE_API_URL` and the Phase 28 CSP); run `alembic upgrade head` as its own explicit step, not automatically on container boot (this repo's production `Dockerfile`/`CMD` deliberately does not auto-migrate — see §11 — unlike `docker-compose.yml`'s dev-only auto-migrate); deploy the backend image/process (`scripts/run_production.sh` or this repo's `Dockerfile`, whose default `CMD` now points at `app.asgi:application`); start the RQ worker(s) (`python -m app.workers.worker`); verify `/health/live` then `/health/ready` both return 200 before routing real traffic to the new instance.

**POST-DEPLOY:** run `python3 -m scripts.production_smoke_test --base-url <real-url> --cors-origin <real-frontend-origin>` (18 automated checks — see §11/§17 of the companion report); manually verify login, registration + email verification, password-reset OTP delivery, and one donor/patient/hospital/family/admin flow each through the real UI against the real deployed backend; verify a real notification is delivered end-to-end for one blood-request creation; verify a real certificate download; verify the storage upload/download flow; verify the graph/haversine-fallback flow behaves as expected for whichever mode (Neo4j configured or not) this deployment uses.
